Spec to Ship

A visual map of the development loop: make the idea legible, turn it into tests, implement against those tests, let the human verify the app, review the code, simplify the result, then ship.

Primary commands: /html-spec · /build-tests · /simplify
Human gates: spec review · test QA · app QA
Goal gates: verify red · implement to green
/html-spec
Create the visual implementation artifact before production code or tests begin.
/build-tests
Translate the approved spec into an executable red test contract, then stop.
/simplify
After green tests and review, reduce complexity while preserving behavior exactly.

    Gates

    These are the stop signs in the process. They keep Codex from racing ahead before the artifact, tests, or app behavior has been checked.

    review
    The HTML spec is discussed in depth with Codex annotations and direct edits until the user says it is ready for tests.
    human QA
    The user checks the spec and test contract manually before implementation begins.
    /goal red
    Codex verifies tests fail for the right reason: missing implementation, not broken test setup.
    /goal green
    Codex implements the approved spec until the focused and relevant broader tests pass.
    app QA
    The user tests the running app themselves. Automated tests do not replace this gate.

    Artifacts

    Each phase leaves behind a concrete object. The repo should make it easy for a later agent to reconstruct what happened and why.

    Artifact Produced By Purpose
    HTML spec /html-spec Visible implementation model, diagrams, states, invariants, open questions, and test contract.
    Review edits Codex annotations User feedback made concrete before tests or code start.
    Red tests /build-tests Executable proof of the approved spec's expected behavior.
    Implementation /goal green Code changed only enough to satisfy the spec and pass verification.
    Review findings Codex review Bugs, regressions, missing tests, and risks resolved before cleanup.
    Simplified diff /simplify Cleaner code with the same externally observable behavior.
    Commit and push ship Final verified result on the remote branch.

    Operating Lanes

    The workflow has three modes of attention. Good runs keep them separate instead of turning everything into implementation work.

    Thinking Artifacts

    HTML specs and annotations make intent visible before code. This is where ambiguous product, prompt, data, or engine behavior becomes discussable.

    command
    /html-spec

    Executable Contract

    Tests translate the approved spec into red checks. The red phase must fail for the right reason before implementation starts.

    command
    /build-tests plus /goal red

    Production Code

    Implementation, review, simplification, and push happen after the contract is clear and the user has checked the important moments.

    command
    /goal green plus /simplify
